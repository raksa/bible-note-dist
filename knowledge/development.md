## Overview

`bible-note` is a Bible-study note editor packaged as a drop-in component. It
extends the [Lexical playground](https://playground.lexical.dev/) editor with
Bible-specific features:

- person (`@`) and place (`#`) mentions backed by the host's datasets, with
  hover cards and a draggable advanced panel;
- Bible verse mentions created by pasting verse text after `^`;
- a lookup panel for browsing both datasets;
- sticky notes, comments, Excalidraw drawings, equations, tables, column
  layouts, collapsibles, media and embeds;
- a footer with Word (`.docx`) import and export, a lossless JSON backup, print
  with page-size preview, read-only mode, and buttons the host adds itself.

The MIT license and Meta's copyright carry over from upstream Lexical.

### The pieces

| Piece                                          | What it is                                                                                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `BibleNote`                                    | The editor. `new BibleNote(props)` then `render(element)`. It mounts its own React root, so the host does not have to be a React app.         |
| `NamesLookupManager`, `LocationsLookupManager` | The datasets behind every mention, hover card, panel and the lookup panel. They have no editor dependency — a host can use them on their own. |
| `BibleNoteSettings`                            | The optional settings panel (gear button), passed to `render`.                                                                                |
| `bible-note/styles.css`                        | The one stylesheet: editor, KaTeX and Excalidraw rules.                                                                                       |
| `bible-note/knowledge/development.md`          | This guide.                                                                                                                                   |
| `bible-note/knowledge/ui-rag.md`               | End-user help for the editor UI, chunked for a retrieval pipeline.                                                                            |

### Bundled vs. supplied by the host

React, React DOM, Bootstrap and bootstrap-icons are **peer dependencies**:

- React must be the host's copy so there is a single instance — a second copy
  breaks hooks.
- Bootstrap and bootstrap-icons are global stylesheets. Shipping them inside the
  package would fix their place in the host's cascade and pin a version the host
  could not theme, so the host installs and imports them itself.

Everything else — Lexical, Excalidraw, KaTeX, Shiki, the Word converters — is
bundled. Lexical and Excalidraw are bundled on purpose: the editor is coupled to
their module instances, and a separately resolved copy could be a different
instance than the one the bundle talks to. `use-sync-external-store` is the one
runtime dependency, left external only so the consumer's bundler converts it
correctly.

The package ships **no datasets**. The host fetches the name and location maps
(and, optionally, verse text) and hands them to the editor.

### Lifecycle in one paragraph

Construct `BibleNote` with the datasets, the storage callbacks and any optional
host hooks; call `render(container)`. Before the first render the editor reads
its own state (settings, comments, read-only mode, zoom) from `storageManager`
and the note itself from `loadData`. From then on every document change goes to
`saveData`, and every other state change to `storageManager`. Methods such as
`content`, `addText` and `searchText` may be called before `render`; writes are
queued until the editor mounts. `unmount()` tears the React root down; the
instance can be rendered again.

<a id="dev-installation-and-stylesheets"></a>

## Installation and stylesheets

```bash
npm install bible-note react react-dom bootstrap bootstrap-icons
```

The peer ranges are those in the package's `package.json`: React and React DOM
`^19.2.8`, Bootstrap `^5.3.8`, bootstrap-icons `^1.13.1`.

### Stylesheet order

Import three stylesheets, in this order — Bootstrap first, then the icon font,
then the editor's own stylesheet last so its overrides win:

```ts
import 'bootstrap/dist/css/bootstrap.min.css';
import 'bootstrap-icons/font/bootstrap-icons.css';
import 'bible-note/styles.css';
```

Skipping the first two does not throw — it renders a broken editor: the toolbar
and footer lose their layout, and with no `@font-face` for the icon font every
`bi bi-*` glyph renders as tofu. `bible-note/styles.css` needs no configuration.

The package's `sideEffects` lists `**/*.css`, so bundlers keep the
`bible-note/styles.css` import; if a custom build strips CSS side effects, the
editor renders unstyled.

### Module formats and entry points

| Import                                                                  | Resolves to                                    |
| ----------------------------------------------------------------------- | ---------------------------------------------- |
| `import … from 'bible-note'`                                            | ES module bundle, with TypeScript declarations |
| `require('bible-note')`                                                 | CommonJS bundle                                |
| `bible-note/styles.css`                                                 | the stylesheet                                 |
| `bible-note/knowledge/development.md`, `bible-note/knowledge/ui-rag.md` | the knowledge files                            |

Shiki grammars, Excalidraw and KaTeX load lazily as separate chunks, so the
initial bundle stays small and those parts load the first time they are used.

### Colour scheme

The editor themes itself through classes on `document.body`
(`playground-theme-light` / `playground-theme-dark`) and Bootstrap's
`data-bs-theme` attribute. Call `bibleNote.setColorScheme('dark')`, or let the
settings panel's Dark Mode switch do it. `applyBibleNoteColorScheme` and
`clearBibleNoteColorScheme` are the bare DOM steps for a host that manages the
body classes itself.

## Quick start

A minimal host: the stylesheets, two datasets, browser storage, and a render.

```tsx
import 'bootstrap/dist/css/bootstrap.min.css';
import 'bootstrap-icons/font/bootstrap-icons.css';
import 'bible-note/styles.css';

import {
  BibleNote,
  BibleNoteSettings,
  createBrowserStorageManager,
  EDITOR_STATE_LOCAL_STORAGE_KEY,
  LocationsLookupManager,
  NamesLookupManager,
} from 'bible-note';

const [namesMap, locationsMap] = await Promise.all([
  fetch('data/KJV/namesMap.json').then((res) => res.json()),
  fetch('data/KJV/locationsMap.json').then((res) => res.json()),
]);

const storageManager = createBrowserStorageManager();

const bibleNote = new BibleNote({
  namesLookupManager: NamesLookupManager.fromRawDataset({ en: namesMap }, 'en'),
  locationsLookupManager: LocationsLookupManager.fromRawDataset(
    { en: locationsMap },
    'en',
  ),
  getLangCode: (text) => (/[ក-៿]/u.test(text) ? 'km' : 'en'),
  editorExtraFontFamilies: [],
  stickyNoteExtraFontFamilies: [],
  storageManager,
  // The note itself: keep it wherever the host keeps documents.
  loadData: async () =>
    (await storageManager.getSetting<string>(EDITOR_STATE_LOCAL_STORAGE_KEY)) ??
    '',
  saveData: async (data) => {
    if (data === '') {
      await storageManager.deleteSetting(EDITOR_STATE_LOCAL_STORAGE_KEY);
    } else {
      await storageManager.setSetting(EDITOR_STATE_LOCAL_STORAGE_KEY, data);
    }
  },
});

bibleNote.render(document.getElementById('root')!, {
  settings: (
    <BibleNoteSettings
      setColorScheme={(mode) => bibleNote.setColorScheme(mode)}
    />
  ),
});
```

The `settings` option takes a React element, so a `.tsx` file is the natural
host. A host without JSX can pass
`React.createElement(BibleNoteSettings, { setColorScheme })` or leave `settings`
out — the editor then simply has no settings panel.

The required props are the two managers, `getLangCode`,
`editorExtraFontFamilies`, `stickyNoteExtraFontFamilies`, `storageManager`,
`loadData` and `saveData`. Everything else is optional and switches a feature
on; the API reference lists each prop.

### Working with a mounted editor

```ts
bibleNote.content; // serialized editor state (JSON string)
bibleNote.content = savedState; // replace the document; '' clears it
bibleNote.addText('^'); // insert as if pasted at the caret
bibleNote.addText('(KJV) Genesis 1:1\n(1): In the beginning God created…');
bibleNote.isReadOnly = true; // lock — the user cannot unlock it
bibleNote.searchText('Moses'); // open the find bar on a query; null closes it
bibleNote.getIsFocusing(); // is the caret in the editor right now?
BibleNote.getAllShortVersesFromText(bibleNote.content); // ['GEN 1:1', …]
```

The two `addText` calls above create a Bible verse mention: verse text pasted
right after a `^` becomes a verse mention instead of a collapsible block.

### Host footer buttons

```tsx
bibleNote.prependFooterActionButton({
  id: 'open-in-app',
  description: 'Open in my app',
  shortcutKey: 'Ctrl+Shift+K',
  children: (
    <button className="action-button" onClick={openInApp}>
      <i className="bi bi-box-arrow-up-right" />
    </button>
  ),
});
bibleNote.removeFooterActionButton('open-in-app');
```

`prepend…` places a button before the built-in footer buttons, `append…` after
them. Re-adding an `id` replaces that button in place. `description` becomes the
tooltip when the element has no `title`; `shortcutKey` clicks the button from
anywhere in the page and is shown in the tooltip. Give the button the
`action-button` class to match the built-in ones.

### Mounting without auto-mount

`render` can be called any time after construction and again later — each call
unmounts the previous root first. Call `unmount()` when the host view goes away;
the instance keeps its props and footer buttons for the next `render`.

## Datasets and lookup managers

The editor ships no data. Every person and place it can mention comes from two
managers the host builds:

```ts
const names = NamesLookupManager.fromRawDataset({ en: namesMap }, 'en');
const locations = LocationsLookupManager.fromRawDataset(
  { en: locationsMap },
  'en',
);
```

`fromRawDataset` takes the generated dataset files exactly as fetched —
`namesMap.json` (`{ version, namesMap, childrenTree, versePersonsMap }`) and
`locationsMap.json` — keyed by a language code, and normalizes them. Records
can be an id-keyed object or an array; anything unrecognised is dropped rather
than trusted. Use the plain constructors only when you already hold normalized
`MentionNameMatch` / `MentionLocationMatch` records.

A manager may hold several languages (`{ en: …, km: … }`); `defaultLang` picks
the one the editor uses, and every query method takes an optional `lang`. The
constructor throws when the default language is missing from the map.

### Records

A name record (`MentionNameMatch`) carries the name, a one-line `title`, a
`description`, family links (`parents`, `children`, `spouses`, `siblings`,
`cousin` — record ids), `locations` (location ids), `verses`, `links`,
`wikipedia`, `gender`, `age`, `years` and a `type` (`person`, `group`, `deity`,
`place`, `concept`, `month`, `supernatural`, `life`, `unknown`). A location
record (`MentionLocationMatch`) carries `type` (`city`, `region`, `mountain`, …),
`coordinates`, `modernIdentification`, `relatedLocations`, `uncertainty` and the
same text, verse and link fields.

`title` and `description` may contain inline reference links the UI renders as
clickable references:

| Link                                 | Points to         |
| ------------------------------------ | ----------------- |
| `[Amram](name-id://<id>)`            | a name record     |
| `[Egypt](location-id://<id>)`        | a location record |
| `[Genesis 1:1](verse-key://GEN 1:1)` | a verse           |
| `[Genesis](book-key://GEN)`          | a book            |
| `[Genesis 14](chapter-key://GEN 14)` | a chapter         |

Verse keys are short keys — a book code plus chapter and verse (`GEN 1:1`,
`1SA 17:1-4`). Ranges are stored collapsed, so the length of `verses` is not a
verse count.

`matterRange` ranks importance: `0` is the most important record and larger is
less important; records without a rank sort last. Every listing and every tie in
a search is ordered by it, then alphabetically.

### Searching

```ts
names.searchNames('Mos', { limit: 20 }); // ranked MentionNameMatch[]
names.searchNames('', { type: 'deity' }); // filter applies before limit
names.searchNamesPagination({ query: 'Mos', page: 2, pageSize: 20 });
names.getRecordById(id);
names.getRecordsByIds(record.children);
names.getRecordsByName('Zechariah'); // names are not unique
names.searchByShortVerse('EXO 6:23'); // the names that verse prints
names.nameTypes; // types present, most common first
locations.searchLocations('Jer', { limit: 10 });
```

Search is a case-insensitive substring match on the name, the KJV English name
and the former name (`oldName`), ranked exact, then prefix, then substring, then
by importance. An empty query lists everything in importance order. Indexes are
built lazily per language on first use and recent queries are cached.

`searchByShortVerse` needs the dataset's verse map (`versePersonsMap` /
`verseLocationsMap`, both included in the generated files).

### Translated datasets

A record in a translated dataset (the Khmer and French mirrors of the KJV data)
carries its translated `name` plus the KJV English name in `kjvName`. The
managers index both, so the same manager answers a query in either language and
ranks an English hit exactly like a native one:

```ts
const names = NamesLookupManager.fromRawDataset({ km: khmerNamesMap }, 'km');
names.searchNames('Genesis'); // finds the record named "លោកុប្បត្តិ"
```

The built-in UI shows the English name beside the translated one in the lookup
panel, the mention typeahead, the hover card and the advanced panel.
`getMentionKjvName(record)` is the rule it uses: the English name, or `null`
when there is nothing to add. An untranslated dataset carries no `kjvName`, and
all of this is a no-op for it.

### Styling a dataset

Both managers take an optional third argument: a React-style CSS object merged
into every surface that renders that dataset — the typeahead popup, the hover
card, the advanced panel and the lookup panel's list and search box. Use it to
give a dataset in another script its own font:

```ts
const locations = LocationsLookupManager.fromRawDataset(
  { km: khmerLocationsMap },
  'km',
  { fontFamily: 'Battambang, serif' },
);
```

The two managers are styled independently. `manager.style` can be read and
reassigned, but plugins read it as they render, so a change only shows up on the
next render. A hover card's own positioning always wins over the style.

### Verse text

The package bundles no Bible text. Three optional props let the host supply it:

- `shortToVerseData(shortKey)` → `{ title, fullText, style? }` — labels verse
  lists in the mention panels and fills the Word export's References appendix.
- `verseFullTextToListShorts(fullText)` → short keys — lets a verse's advanced
  panel show the people and places that verse mentions.
- `changeBibleKey(event, fullText)` — makes the version label in a verse panel a
  button that opens the same verse in another version.

`fullText` is the shape the editor accepts when Bible text is pasted after `^`:
a title line such as `(KJV) Genesis 1:1`, then one line per verse such as
`(1): In the beginning…`.

`BibleNote.getAllShortVersesFromText(text)` goes the other way: it lists every
verse a note refers to — verse mentions and references typed in the prose — as
short keys, in document order without duplicates. Ranges inside one chapter are
expanded verse by verse; a range crossing chapters keeps only its endpoints.

### Your own lookup UI

The managers carry no editor dependency. To build a custom mention picker or a
search page, construct them and call their methods — no `BibleNote` import is
needed, and the results are exactly what the built-in UI shows.

## Persistence and storage

The editor splits what it stores into two channels.

| Channel      | Carries                                               | Host hook               |
| ------------ | ----------------------------------------------------- | ----------------------- |
| The note     | the serialized Lexical editor state of the document   | `loadData` / `saveData` |
| Editor state | settings, comments, read-only mode, zoom, panel state | `storageManager`        |

### The note: `loadData` and `saveData`

`saveData(data)` is called on every change to the document with the serialized
editor state — a JSON string, the same one `bibleNote.content` returns. It is
called with `''` when a stored note turns out to be unreadable and is discarded.
`loadData()` returns that string (or `null` / `''` for an empty editor) and may
be async. Store it wherever the host keeps documents: a file, a database row, a
server.

Because `saveData` runs on every change, debounce it on the host side if the
store is expensive. The string is also the lossless format: the footer's Export
button downloads it, Import reads it back, and assigning `bibleNote.content`
replaces the document with it.

### Editor state: `storageManager`

A `BibleNoteStorageManager` is three async methods — `getSetting`, `setSetting`,
`deleteSetting` — over string values. `createBrowserStorageManager()` is the
`localStorage` implementation; an Electron or server-backed host can implement
the same three methods over its own store.

Before the editor first renders it reads every key in
`BIBLE_NOTE_STORAGE_MANAGER_KEYS` from the storage manager, then serves reads
from memory; every write goes straight through to `setSetting`, fire-and-forget.
The keys:

| Key                                          | Holds                                                                      |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| `lexical-playground-settings`                | the settings panel's switches                                              |
| `lexical-playground-editor-state`            | the note — routed to `loadData` / `saveData`, never to the storage manager |
| `lexical-playground-comments`                | comment threads                                                            |
| `lexical-playground-comments-panel-open`     | whether the comments panel is open                                         |
| `lexical-playground-block-text-links`        | the "link block text" connections                                          |
| `lexical-playground-read-only-mode`          | whether the user locked the note                                           |
| `lexical-playground-insert-character-picker` | the Emoji & HTML Character picker's state                                  |
| `lexical-playground-editor-zoom-percent`     | the zoom level                                                             |

The `lexical-playground-` prefix is inherited from the upstream playground; keep
it when migrating stored data.

The editor-state key is exported as `EDITOR_STATE_LOCAL_STORAGE_KEY`. The quick
start reuses it to keep the note in the same store as everything else, which is
fine for a single-note host; a multi-note host keeps each note under its own key
or file and returns the right one from `loadData`.

### Read-only mode

The user can lock a note from the footer, and that choice persists under
`lexical-playground-read-only-mode`. A host can force it: `bibleNote.isReadOnly
= true` locks the note, turns the footer button into **Read-Only Mode Locked**,
and the user cannot unlock it until the host assigns `false`.

### Share links

Outside an app (`isOnApp` false), the footer's **Share as Link** button encodes
the note into the page URL's `editor-state` query parameter, optionally
password-protected; opening such a URL loads that note. Hosts that embed the
editor in an app set `isOnApp: true`, which hides the button.

## Host integration

Every optional prop switches on one integration. This topic groups them by
feature; the API reference has the exact signatures.

### Fonts and languages

- `editorExtraFontFamilies: [['Battambang', 'km'], …]` adds fonts to the
  toolbar's font menu and to Excalidraw, each tagged with a language code. The
  host loads the font faces itself (a `@font-face` or a webfont link).
- `getLangCode(text)` returns a language code for a piece of text. When it
  returns something other than `'en'`, pasted Bible text and Excalidraw text
  switch to the first extra font registered for that language — so Khmer verse
  text renders in a Khmer font automatically.
- `stickyNoteExtraFontFamilies: ['"Fasthand"', …]` adds CSS font-family values
  to the sticky-note font picker.
- A lookup manager's style object (`{ fontFamily }`) styles one dataset across
  the mention UI; see the datasets topic.

### Media files

By default a picked or dropped image, video, audio or PDF is embedded in the
note as a data URL. Two hooks change that:

- `resolveFilePath(file, { source })` returns a path or URL to store instead —
  for example the file's location on disk in Electron, or an upload URL. `source`
  is `'drop'` (dropped or pasted) or `'file-input'` (picked in the media dialog).
  Return `null` to fall back to embedding.
- `revealFile(path)` shows a local file to the user (Electron:
  `shell.showItemInFolder`). With it, a selected media item whose source is a
  local path gets a reveal button.

### Excalidraw libraries

The editor bundles a Christian-themed Excalidraw library. `excalidrawLibraryItems`
adds library items of the host's own. To persist libraries the user imports
inside Excalidraw, implement the trio:

- `excalidrawSaveLibrariesFile(json)` — store one serialized library;
- `excalidrawLoadLibrariesFileList()` — return the stored libraries, read when
  the Excalidraw editor opens;
- `excalidrawClearLibrariesFileList()` — forget them all.

The demo host keeps the list as a JSON array in `localStorage`.

### Settings panel

`render(el, { settings: <BibleNoteSettings setColorScheme={…} /> })` adds the
gear button and its switches. Without `settings` there is no settings panel and
every setting keeps its default. `settingsContainerElement` portals the panel
elsewhere in the page (the demo puts it in a fixed container of its own).
Settings persist through the storage manager. The switches, their keys and
defaults:

| Switch | Setting | Default |
| --- | --- | --- |
| Measure Perf | `measureTypingPerf` | Off |
| Debug View | `showTreeView` | Off |
| Dark Mode | `isDarkMode` | Off |
| Show invisible characters | `showInvisibleCharacters` | Off |
| Nested Editors Debug View | `showNestedEditorTreeView` | Off |
| Rich Text | `isRichText` | On |
| Nested Tables | `hasNestedTables` | Off |
| Char Limit | `isCharLimit` | Off |
| Char Limit (UTF-8) | `isCharLimitUtf8` | Off |
| Link Attributes | `hasLinkAttributes` | Off |
| Max Length | `isMaxLength` | Off |
| Autocomplete | `isAutocomplete` | On |
| Table Of Contents | `showTableOfContents` | Off |
| Use Lexical Context Menu | `shouldUseLexicalContextMenu` | Off |
| Preserve newlines in Markdown | `shouldPreserveNewLinesInMarkdown` | Off |
| Use Brackets for Highlighting | `shouldAllowHighlightingWithBrackets` | Off |
| Retain selection | `selectionAlwaysOnDisplay` | Off |
| Enable Code Highlighting | `isCodeHighlighted` | On |
| Use Shiki for Code Highlighting | `isCodeShiki` | Off |

Pass `setColorScheme={(mode) => bibleNote.setColorScheme(mode)}` so the
instance's `colorScheme` follows the Dark Mode switch.

### Footer modes

- `isOnApp: true` — the editor runs inside an app, not a web page: hides
  **Share as Link** and **Convert From Markdown**.
- `isMinimize: true` — compact footer: Import, Export and Editor Information
  move into a **More actions** menu.
- `print()` — replaces the built-in printing (which lays the note out at the
  selected page size and opens the print dialog).

Host buttons go before or after the built-in ones with
`prependFooterActionButton` / `appendFooterActionButton`.

### Electron: native file dialogs

When the page exposes `window.bibleNoteDesktop`, the footer's Word import/export
and JSON Import/Export use native Open and Save dialogs instead of a browser
file picker and download. The contract (this repository's
`scripts/electron-preload.cjs` implements it with `contextBridge` and two
`ipcMain` handlers):

```ts
window.bibleNoteDesktop = {
  isElectron: true,
  openFile(options: { filters: { name: string; extensions: string[] }[] }):
    Promise<{ canceled: true } | { canceled: false; data: Uint8Array; fileName: string }>,
  saveFile(options: {
    data: Uint8Array | string;
    defaultFileName: string;
    filters: { name: string; extensions: string[] }[];
  }): Promise<{ canceled: true } | { canceled: false; fileName: string }>,
};
```

The bridge is detected by `isElectron === true`. It is independent of
`isOnApp` — the demo host sets `isOnApp` from whether the bridge exists, which
is a reasonable default.

### Word round trips

The footer's Word buttons export a standard `.docx` that also embeds a private
BibleNote copy of the editor state; importing that file restores the full
editable document. A `.docx` from elsewhere (or one Word has stripped) is
converted from its Word content: text, headings, emphasis, lists, tables, links
and images survive, Word-only layout may be simplified.

Because a Word document has no hover cards, the export adds a **References**
appendix: every person, place and verse mention links to an entry with the
record's details and the verse text. Verse references are resolved through
`shortToVerseData` and related people and places through
`verseFullTextToListShorts`, so supply both for a complete appendix. Equations
become editable Word equations; sticky notes, drawings and embed thumbnails
become pictures.

## Working on the editor UI

This topic is for changing the editor itself, in its source repository.

### Layout

| Path                                         | What lives there                                                                       |
| -------------------------------------------- | -------------------------------------------------------------------------------------- |
| `src/lib.ts`                                 | the package's public entry — only re-exports; everything it reaches is library code    |
| `src/index.tsx`                              | the demo host (fetches datasets, wires every prop, mounts) — not part of the package   |
| `src/BibleNote.ts`                           | the `BibleNote` class: queued editor actions, footer buttons, colour scheme            |
| `src/bibleNoteHelpers.tsx`                   | `BibleNoteProps`, the storage split, `renderEditor`                                    |
| `src/AppComp.tsx`                            | providers, storage hydration, the editor controller behind `BibleNote`'s methods       |
| `src/Editor.tsx`                             | the plugin tree, zoom and the full-view layout                                         |
| `src/plugins/<Name>Plugin/`                  | one Lexical plugin per folder                                                          |
| `src/nodes/`                                 | custom Lexical nodes (`PlaygroundNodes.ts` registers them)                             |
| `src/ui/`                                    | shared UI: modals, dropdowns, colour picker, Excalidraw modal, equation editor         |
| `src/context/`                               | React contexts: settings, toolbar state, lookup managers, verse actions, media actions |
| `src/themes/`                                | the Lexical editor themes and their SCSS                                               |

### Adding a feature

A typical new block or inline feature touches:

1. a node in `src/nodes/`, registered in `src/nodes/PlaygroundNodes.ts`;
2. a plugin folder in `src/plugins/`, mounted in `src/Editor.tsx` (behind a
   setting if it is optional — add the key to `DEFAULT_SETTINGS` in
   `src/appSettings.ts` and a `<Switch>` in `src/Settings.tsx`);
3. a slash-menu option in `getBaseOptions()` in
   `src/plugins/ComponentPickerPlugin/index.tsx` and/or an item in the toolbar's
   Insert dropdown;
4. a shortcut in `SHORTCUTS` (`src/plugins/ShortcutsPlugin/shortcuts.ts`) and its
   handler in the shortcuts plugin, if it has one;
5. theme classes in `src/themes/PlaygroundEditorTheme.ts` and SCSS;
6. any persisted state through `getBibleNoteStorage()` (`src/storageManager.ts`),
   with the key added to `BIBLE_NOTE_STORAGE_MANAGER_KEYS` so it is hydrated
   before the first render;
7. Word export/import handling in `src/utils/docx*` if the node needs a Word form;
8. the user-facing description in `knowledge/ui/` (see "The knowledge files"
   below).

UI follows the existing conventions: Bootstrap utility classes, `bi bi-*` icons
from bootstrap-icons (a peer dependency — never import its CSS from library
code), and colours that work under both `playground-theme-light` and
`playground-theme-dark`.

## Building and releasing the package

### `npm run pack`

`scripts/pack.mjs` builds `packages/bible-note/`:

1. wipes the generated directories — `dist/`, `types/`, `knowledge/`;
2. bundles `src/lib.ts` twice with `vite.lib.config.ts`, once as ESM (`.mjs`)
   and once as CommonJS (`.cjs`), plus the single `dist/bible-note.css`;
3. emits declarations with `tsc -p tsconfig.lib.json` and prunes them to what
   `types/lib.d.ts` actually reaches;
4. builds `knowledge/development.md` and `knowledge/ui-rag.md`;
5. checks the static `package.json` against the build and the root manifest —
   every advertised path exists, `files` and `sideEffects` are right, peer
   ranges match the root `package.json`, external packages are declared;
6. checks the entry surface (required exports present, no peer CSS bundled, no
   throwing `require()` polyfill in the ES build) and type-checks the packaged
   declarations from outside the repository, as a consumer would see them.

Any failure stops the run with the exact mismatch.

### Hand-maintained files

`packages/bible-note/package.json`, `README.md` and `LICENSE` are the only files
in `packages/` that git tracks, and no script writes them:

- bump `version` whenever library code changes — patch for fixes and internal
  changes, minor for new exports, options or published files, major for a
  breaking change to the public surface;
- update the README when a change is visible to a consumer (a new export goes
  in its Exports table);
- edit `package.json` by hand when peer ranges change in the root manifest or
  entry points move — `pack` reports the exact drift.

### Testing the built package

`test-packages/` installs `bible-note` from `../packages/bible-note`. After
`npm run pack`, run `npm i` and `npm run vite` (port 3007) there to use the
tarball contents exactly as a consumer would. `npm run copy-packages` mirrors
the publishable files into the sibling `../bible-note-dist` checkout
(`npm run pack:copy` does both).

### Publishing

From a clean `main`, with the package built:

```bash
npm pack --dry-run                          # check the file list
npm whoami                                  # npm login if this fails
npm version patch --tag-version-prefix=""   # or minor / major
npm publish
git push origin main --follow-tags
npm view bible-note version
```

### Classes

#### `BibleNote`

The BibleNote editor. Construct it with the host's datasets and storage
callbacks, then [`render`](#api-biblenote) it into an element.

Every editor-backed method (`content`, `addText`, `searchText`, …) can be
called before `render`: writes are queued and applied once the editor has
mounted, and reads return an empty value until then.

```ts
new BibleNote(...)
constructor(props: BibleNoteProps);
```

##### `BibleNote.VERSION`

```ts
static VERSION: string;
```

The package version this bundle was built from.

##### `BibleNote.getAllShortVersesFromText()`

```ts
static getAllShortVersesFromText(lexicalText: string): Array<string>;
```

Every short verse reference (`GEN 1:1`) the given note content mentions, in
document order and without duplicates. Takes what `content` returns — a
serialized editor state — or plain text, and reads both the Bible verse
mentions and any reference written in the prose. Ranges inside one chapter
are expanded verse by verse; a range crossing a chapter boundary keeps only
its endpoints, because per-chapter verse counts are not bundled here.

##### `props`

```ts
props: Readonly<BibleNoteProps>;
```

The props the instance was constructed with.

##### `colorScheme`

```ts
colorScheme: BibleNoteColorScheme;
```

The colour scheme last applied — by [`BibleNote.setColorScheme`](#api-biblenote) or the
settings panel's Dark Mode switch. Read it; change it with `setColorScheme`.

##### `content`

```ts
get content(): string;
set content(value: string);
```

The note as a serialized Lexical editor state (a JSON string) — the same
string `saveData` receives. Reads `''` until the editor has mounted.
Assigning replaces the whole document; assigning `''` clears it.

##### `isReadOnly`

```ts
get isReadOnly(): boolean;
set isReadOnly(value: boolean);
```

Whether the note is locked against editing. Assigning `true` forces
read-only mode: the footer's lock turns into **Read-Only Mode Locked** and
the user cannot unlock it. Assigning `false` releases that lock and makes
the note editable.

##### `getIsFocusing()`

```ts
getIsFocusing(): boolean;
```

Whether the caret is in the editor right now: the window has focus, the
editor is the active element, and the selection is a collapsed caret inside
it. A host can use this to decide whether to send text to `addText`.

##### `setColorScheme()`

```ts
setColorScheme(mode: BibleNoteColorScheme): void;
```

Switches the editor between light and dark. Applies the body classes at
once (see `applyBibleNoteColorScheme`) and keeps the settings panel's Dark
Mode switch in step.

##### `addText()`

```ts
addText(text: string): void;
```

Inserts text at the caret, or at the end of the note when there is no
selection, exactly as if the user had pasted it as plain text — so the
paste rules apply: Bible text pasted right after a `^` becomes a verse
mention. Ignored while the note is read-only or when `text` is empty.

##### `appendFooterActionButton()`

```ts
appendFooterActionButton(actionButton: BibleNoteFooterActionButton): void;
```

Adds a host button after the footer's built-in buttons. A button whose `id`
is already present is replaced in place, keeping its position.

##### `prependFooterActionButton()`

```ts
prependFooterActionButton(actionButton: BibleNoteFooterActionButton): void;
```

Adds a host button before the footer's built-in buttons, ahead of any
prepended earlier. A button whose `id` is already present is replaced in
place, keeping its position.

##### `getFooterActionButton()`

```ts
getFooterActionButton(id: string): BibleNoteFooterActionButton | null;
```

The host footer button with this `id`, or `null`.

##### `removeFooterActionButton()`

```ts
removeFooterActionButton(id: string): boolean;
```

Removes the host footer button with this `id`; `false` when there was none.

##### `searchText()`

```ts
searchText(query: string | null): void;
```

Drives the editor's find bar. A string opens the bar (or updates the query
if it is already open); `null` closes it. Queued until the editor mounts,
like the other editor-backed methods.

##### `render()`

```ts
render(containerElement: HTMLElement, options?: BibleNoteRenderOptions): void;
```

Mounts the editor into `containerElement` with its own React root.
Rendering again unmounts the previous root first, so an instance is only
ever mounted once.

##### `unmount()`

```ts
unmount(): void;
```

Unmounts the editor. The instance keeps its props and footer buttons and
can be rendered again.
